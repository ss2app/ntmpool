# 零停机运维 + 崩溃恢复设计

> 老板 2026-07-06 两问：① 运行中的矿池要新增币，怎么不停机/无损？② 矿池在打款在途（tx 刚进 mempool）或爆块未记录时崩溃/重启，怎么办？
> 本文是这两个问题的完整答案，M1 起按此实现。

## 一、不停机加币：分三档，绝大多数情况根本不用动二进制

### 档位 1（最常见）：纯配置热添加，零中断

新币如果用的是**已有的节点适配器 + 已有算法 + 已有方言**（工厂大多数币：标准 bitcoin-rpc 分叉币、门罗系魔改……），那么加币 = 管理后台 API 提交一段币配置：

```
POST /admin/v1/coins        ← 新增 CoinInstance：起 notifier/jobmanager/端口监听
DELETE /admin/v1/coins/{id} ← 下线：先停新连接 → 排空 → 停打款 → 停实例
```

进程不重启，老币的矿工**完全无感**。这是与 miningcore 的决定性差异（miningcore 加币要改 config.json + 手工建分区表 + 重启全进程）。每币一个独立 goroutine 树、独立生命周期，架构上第一天就这么设计（02-架构设计 §0）。

### 档位 2：新算法也尽量不换二进制 —— 通用 FFI 插件

新币若只是**算法**是新的（节点还是标准 RPC），走通用 C ABI 插件：

```c
// NTMPool hasher 插件 ABI（v1）
int ntm_hash(const uint8_t* input, size_t len, uint8_t* out32);
```

- 新算法编译成符合此 ABI 的 `.so`/`.dll`（往往就是把链官方的共识库包一层，天然满足「与节点同源」铁律）；
- 币配置里给 `hasherLib: "/data/ntmpool/lib/libnewcoin.so"` + **金锚 test vector**（input/output hex）——加载时先跑自检，不过不加载；
- dlopen 是运行时的，照样档位 1 热添加。
- ⚠ 有状态算法（RandomX 类要 seed/epoch/VM 池）ABI 会扩展（init/destroy/set_seed），M3 定稿。

### 档位 3：真要换二进制（核心代码升级），三招

**先破除一个焦虑：矿池短暂重启对矿工几乎无感。** 调研坐实（docs/04 §6）：所有主流锄头都有自动重连——XMRig 5s×5 次重试、T-Rex/cgminer 断线重连+主池恢复自动切回；锄头判「池死」的窗口约 60s。所以**只要重启 < 10 秒，矿工连备用池都不会切**，损失只有在飞的几秒份额。share/余额/块记录全在 Postgres，进程重启不丢账。

在此之上按需选：

| 招 | 中断 | 做法 | 期 |
|---|---|---|---|
| **快速重启** | 连接闪断几秒，矿工自动重连 | systemd restart；锄头无感窗口内完成 | M1 即有 |
| **优雅二进制升级**（nginx 同款） | 零中断：存量连接不断 | 新进程继承监听 socket fd 接管 accept，老进程停止 accept、排空存量连接后退（Go 现成方案 cloudflare/tableflip；Windows 不支持 fd 传递，生产在 Linux 无碍） | M2 |
| **多实例蓝绿** | 真正零感知 | 两实例共享 Postgres，前置转发器（hk.tutuit.xyz 架构现成）把新连接切到 B → 升级 A → 切回；分批迁移 | M4 |

推荐运维姿势：日常升级用「优雅升级」；大版本用「蓝绿」；档位 1/2 覆盖 90% 的加币需求，根本走不到这一步。

## 二、崩溃恢复：核心原则 = 意图先落库，动作后执行

任何「对外的钱/块动作」执行前，先把**意图**写进 Postgres（本地写库毫秒级），动作完成后再更新状态。崩溃后重启第一件事是**恢复扫描**：把每个「悬着的意图」和链上真实状态对账，一一归位。逐场景：

### 场景 A：打款崩溃（你问的「刚提交到 mempool」）

最危险的窗口是「**广播了但 txid 没记下来**」——不知道钱打没打出去，盲目重发=双花双付，盲目作废=矿工白扣余额。

**根治（bitcoin 系，M1 实现）：拆步打款，txid 在广播前就确定**：

```
① DB 事务：扣余额 + 建 batch/payments(status=created)
② 构造并签名交易（createraw→fundraw→signraw，不广播）——SegWit 后签名即定 txid
③ 落库：batch 记 plannedtxid + rawtx（status=prepared）
④ 广播 sendrawtransaction（幂等：already-in-mempool/already-known 视为成功）
⑤ status=sent → 确认追踪 → confirmed
```

崩在任何一步，重启恢复都无歧义：
- 崩在 ①②之间/②③之间：库里 created 无 rawtx → 交易从未存在 → 安全回滚余额或重新准备；
- 崩在 ③④之间/④⑤之间：库里有 plannedtxid → **拿它查 mempool/链**（getrawtransaction/gettransaction）：查到 = 已广播，直接续 sent 流程；查不到 = 没广播出去，把落库的 rawtx **原样重播**（同一笔签名交易，同 txid，天然幂等，不可能双花）。

**你问的具体情况**：tx 刚进 mempool 池就崩了——完全没事。交易已经交给链网络了，矿工照常打包，钱照常到账（余额在①就扣了，不会重复打）；池重启后按 plannedtxid 查到它，继续确认追踪即可。

**不支持 raw tx 拆步的链**（门罗系/自定义链，sendmany 构造+广播一步完成）：崩溃窗口内的 batch 标 `unknown` + 告警 + **冻结该币打款**，管理后台提供「钱包近期转出 vs batch 输出集合」比对工具，人工点「确认已发（补 txid）」或「确认未发（重发）」。绝不自动重发（铁律，pitfall C4 的 4 笔双花就是自动重试打出来的）。

### 场景 B：爆块崩溃（你问的「爆块了但没被记录」）

先说清楚丢的是什么：块本身提交给节点后就进链了，**coinbase 奖励一定会到池钱包，钱不会丢**；丢的是池 DB 里的 round 记录——没有记录就不会给矿工分账，矿工白干一轮，砸的是池的信誉。

双保险：

1. **先记后交**：命中全网难度 → 先写 `blocks(status=submitting)`（本地毫秒级，不耽误传播）→ 再向所有健康节点并发 submitblock → 成功后转 `pending`。重启恢复扫描所有 `submitting`：查链上该高度块 hash == 我们的 hash？是 → 转 pending 正常走成熟/分账流程；不是 → 标 submit-failed（share 权重已计，矿工不吃亏）。

2. **钱包 coinbase 审计兜底**（守恒对账器的一部分，每打款周期跑）：扫池钱包收到的 generate/coinbase 收入，与 blocks 表比对。发现「钱包收到挖矿收入但 blocks 表无记录」（极端崩溃、或 1 都没兜住的情况）→ 告警 + 管理后台一键**补建 round**：用 shares 表明细重建当时的 PPLNS 窗口分账——**shares 明细保留 3 天（而非只留内存）就是为这一刻**。

### 场景 C：share 与统计

- share 批量写库（每秒 flush 一批）：崩溃最多丢 ~1 秒的份额权重，对 PPLNS 影响可忽略；**爆块 share 例外，同步落库**（它属于场景 B 的意图记录）。
- vardiff/连接状态是纯内存，重启后矿工重连从 startDiff 重新收敛（几十秒），可接受；PPLNS 窗口、余额、债务全在库里，零丢失。

### 场景 D：恢复扫描清单（重启时固定顺序执行，M1 代码化）

```
1. blocks: submitting → 链上比对 → pending / submit-failed
2. batches: prepared/sent 无确认 → plannedtxid 查链 → 续流程 / 重播 rawtx
3. batches: created 无 rawtx → 回滚或重备
4. (无 raw tx 链) unknown batch → 冻结打款 + 告警人工
5. 守恒对账一轮（含 coinbase 审计）→ 不平则冻结打款 + 告警
6. 一切干净 → 恢复正常运行
```

## 三、落到代码的改动（本次已做）

- `db/schema.sql`：blocks.status 增加 `submitting`；payment_batches 增加 `plannedtxid`/`rawtx` 列、status 注释增加 `prepared/unknown`。
- `internal/adapter`：新增可选接口 `RawTxWallet`（PrepareSendMany 签名不广播 + Broadcast 幂等重播）；打款引擎优先走它，不支持的链退回 SendMany+unknown 恢复。
- `internal/adapter/bitcoinrpc`：M1 第一个真实适配器（见源码）。
