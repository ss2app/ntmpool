# 11 — 复式账本（append-only journal）立项设计

> 对应 docs/10 §2 C1（批次3）。铁律：**生产已验证的账本不可轻动**——本设计走渐进式，
> 任何阶段都不改变现有会计语义，直到影子对拍长期 delta=0 才翻转权威。
> 状态：**立项评审稿（2026-07-17，Claude 起草，待用户拍板后 codex 分批实现）**。

## 0. 一句话结论

现有账本的「余额可从事件日志完整重放」**已实测成立**（PG 侧全部余额变动走单一咽喉
`addBalanceTx` = UPSERT+`balance_changes` 同事务；2026-07-17 对 dragonx/btc09 两生产库
只读核对逐地址零失配，见 §3-阶段0）；真正缺的是**配平的另一条腿**
（费计提/债务/块收入都只在投影表里，不在事件流）。因此方案 = 三阶段渐进：
**先把已有事件流验证成不变量（阶段0，极小改动）→ 影子双写配平 journal（阶段1，本立项主体）
→ 权威翻转（阶段2，仅改「谁说了算」）**。绝不推倒重写。

## 1. 现状盘点（2026-07-17 逐行核对 pgledger.go/memledger.go/schema.sql）

### 1.1 已经做对的（复式账本要继承、不许破坏）

| 机制 | 位置 | 对复式账本的意义 |
|---|---|---|
| 全部余额变动走 `addBalanceTx`（UPSERT+流水同事务） | pgledger.go:1013 | 事件流「矿工侧单腿」已完备，写入口唯一 |
| `balance_changes` 永久保留、带 usage+tags | schema.sql:61 | 半个 journal 已存在；`TotalPaid` 已是事件推导值 |
| `block_credits` 抵债前全额快照 + reversed 标志 | schema.sql:74 | 每块 allocation 快照 = 孤块补偿分录的唯一依据（已符合「不删历史」） |
| RefundPayout 用流水 tag 查重做 batch 级幂等 | pgledger.go:666 | 「business_key 防重复入账」的先例 |
| Reconcile 守恒式 + 破则冻结 | pgledger.go:746 | 全局不变量已在产；journal 只是把它拆细到每笔 |
| Confirm/Orphan 单事务 + FOR UPDATE + 状态幂等 | pgledger.go:303/467 | 崩溃窗口已闭合；journal 同事务写入即无新窗口 |

### 1.2 距真复式账本的缺口（本立项要补的）

1. **单腿记账**：`balance_changes` 只记矿工侧。费计提在 `blocks.feeamount`（随 status 翻转
   隐式出入账）、债务在 `debts.remaining`（原地改写）、块收入只是 `blocks.reward` —— 都不在
   事件流里。孤块时「扣不动的部分」去了哪，账上无显式科目（守恒式靠 debts_net 吸收）。
2. **抵债瞬间不留痕**：ConfirmBlock 里 `offsetDebtsTx` 把还债部分从 credit 里扣掉后才写
   "reward" 流水——债务偿还这个经济事件本身没有事件行（schema 注释里的 `debt_repay`
   usage 从未被写过）。
3. **无 journal 级配平约束**：没有「每笔业务事件借贷必须相等」的机械校验——守恒式是全局周期
   校验，单笔错账要等下轮 Reconcile 才炸，且炸了不知道是哪笔。
4. **Mem 实现零事件流**：MemLedger 是纯 map 投影（noctari 等 mem 币），无任何可重放依据。
5. **人工调账无强制配平**：`manual_credit/manual_debit` usage 预留了但没有「必须挂对手科目」
   的约束（Q5 铁律：禁止裸的「余额加 10」）。

### 1.3 明确的非目标（本立项不做）

- **不做 PPS/FPPS 资本模型**（Q8-T）——NTMPool 只有 PPLNS/SOLO/直付。
- **不做每 share 一笔分录**（Q1 §4.6 明确建议按块/批次级）——PPLNS 本来就是块级入账。
- **不把钱包资产纳入 journal**——钱包侧真相由批次2 的 chain-to-book 审计（B1）覆盖，
  journal 只管「账内」；两者在 Reconcile 处交汇。
- **不改打款状态机**（docs/05 已生产验证）；不改 PPLNS 分账算法与取整语义（分毫不动）。
- **不回填历史**——同 B3 的 legacy-unversioned 原则：历史无法可靠反推，诚实起账（见 §5）。

## 2. 目标模型

### 2.1 表结构（新增两张表 + 投影不动）

```sql
-- 每笔业务事件一行（= 一个借贷配平的 journal transaction）
CREATE TABLE IF NOT EXISTS journal_tx (
    id           BIGSERIAL PRIMARY KEY,
    poolid       TEXT NOT NULL,
    business_key TEXT NOT NULL,   -- 幂等键，见 §2.3；同池唯一
    kind         TEXT NOT NULL,   -- confirm|orphan|deduct|refund|direct_confirm|fee_collect|debt_writeoff|manual|opening
    policy_version TEXT NOT NULL, -- 结算策略版本（B3 配套：journal 天然带版本戳）
    memo         TEXT NULL,
    created      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (poolid, business_key)
);

-- 每笔事件的分录腿（Σamount 必须 = 0，代码在同事务内断言后才 commit）
CREATE TABLE IF NOT EXISTS journal_entry (
    id           BIGSERIAL PRIMARY KEY,
    txref        BIGINT NOT NULL REFERENCES journal_tx(id),
    poolid       TEXT NOT NULL,
    account      TEXT NOT NULL,   -- 科目，见 §2.2
    address      TEXT NULL,       -- 地址维度科目（miner:payable / debt:receivable）才填
    amount       NUMERIC NOT NULL -- 正=借 DR，负=贷 CR（约定：负债类科目增加记贷）
);
CREATE INDEX IF NOT EXISTS idx_journal_entry_acct ON journal_entry(poolid, account, address);
```

分录**不更新、不删除**；更正只允许新增补偿 journal_tx（kind=manual，business_key 带
config_audit id）。

### 2.2 科目表（最小可用集，从 Q1 §4.6 / Q5 §4.4 裁剪到 NTMPool 实际业务）

| 科目 | 维度 | 类型 | 对应现有投影 |
|---|---|---|---|
| `block:revenue` | 池 | 收入 | Σ blocks.reward WHERE confirmed |
| `miner:payable` | 地址 | 负债 | balances.amount |
| `pool:fee_accrued` | 池 | 收入 | Σ blocks.feeamount WHERE confirmed |
| `payout:settled` | 池 | 出账累计 | −Σ balance_changes usage∈(payment,payment_refund) |
| `payout:in_transit` | 批次(memo) | 负债 | **预留**（阶段2+ 可选，需引擎终态回调，见 §2.3-4） |
| `debt:receivable` | 地址 | 资产 | debts.remaining |
| `orphan:loss` | 池 | 费用 | **新**（今天隐没在守恒式里） |
| `incident:loss` / `recipient:receivable` | 地址 | 费用/资产 | **新**（B2 错误追回用） |
| `opening:equity` | 池 | 权益 | **新**（起账快照对手方） |

### 2.3 现有业务事件 → 分录映射（严格按现行代码语义再表达，不改任何数值）

business_key 约定：`confirm:block:<hash>` / `orphan:block:<hash>` / `deduct:batch:<n>` /
`refund:batch:<n>` / `feecollect:batch:<n>` / `manual:<audit_id>` / `opening:<date>`。

1. **ConfirmBlock（普通/SOLO）**（pgledger.go:303）
   DR `block:revenue` R ｜ CR `miner:payable`(a) net_a、CR `pool:fee_accrued` F、
   CR `debt:receivable`(a) repaid_a。
   恒等式 R = Σnet + F + Σrepaid 由现行代码保证（credit=amt−repaid），journal 只是显式化。
2. **ConfirmBlock（直付，midstate）**（pgledger.go:406）
   同上入账腿 + 直付腿：DR `miner:payable`(a) paid_a ｜ CR `payout:settled`。
   （对应现有 usage='payment' 行 + batchid=−blockID 的 payments 展示行。）
3. **OrphanBlock（已确认块回滚）**（pgledger.go:467）
   DR `miner:payable`(a) take_a、DR `debt:receivable`(a) remain_a、DR `pool:fee_accrued` F
   ｜ CR `block:revenue` R。
   **精确配平**：Σtake+Σremain = Σamt（block_credits 全额快照）= R−F，故三腿之和恒 = R，
   无残差（起草稿曾误以为需要 loss 腿，推导后确认现行语义天然配平）。
   confirm 时已被抵债的部分孤块不恢复（现行语义）——净效果在 payable/debt 两科目上
   自洽轧平，journal 无需特殊腿。`orphan:loss` 科目**不在孤块分录里用**，专留给 B2 的
   坏账核销（DR `orphan:loss` ｜ CR `debt:receivable`）。直付块孤块的 paid 退回腿：
   DR `payout:settled` ｜ CR `miner:payable`(a)（对应现有 payment_refund 行）。
4. **DeductForPayout**（pgledger.go:633）
   DR `miner:payable`(a) amt_a ｜ CR `payout:settled`。
   ★沿用现行语义：扣款即计入已付（今天的 usage='payment' 就是这个口径，在途批次
   由 payment_batches 状态机单独管）。`payout:in_transit` 科目**阶段1 不启用**——启用它
   需要打款引擎在批次 confirmed 时新增一个回调账本的耦合点（今天引擎终态不通知
   Ledger），属阶段2+ 可选精化，不值得为它在影子期引入新接线。
5. **RefundPayout**（pgledger.go:659）
   DR `payout:settled` ｜ CR `miner:payable`(a)（幂等键从 balance_changes tag 查重升级为
   journal business_key UNIQUE——数据库级防双退）。
7. **手续费归集**（engine.autoFeeCollect）——**不入 journal**。
   归集是钱包侧资金搬运（金库→费地址），不改任何账内债权债务；强行入账会破坏
   `pool:fee_accrued == Σ blocks.feeamount(confirmed)` 的投影恒等式（起草稿踩过这个
   推导坑）。UncollectedFees 口径照旧 = fee_accrued − Σ fee_collect 批次（batches 侧），
   钱包侧真实性由 B1 chain-to-book 覆盖——与「钱包资产不入 journal」非目标一致。
8. **B2 结构化事件（并入本设计，替代裸负余额）**
   多打/打错：DR `recipient:receivable`(收错方) ｜ CR `incident:loss` 或 CR `miner:payable`
   （按追回策略 policy_version 决定）；坏账核销：DR `incident:loss` ｜ CR `recipient:receivable`。
   debts 追缴策略版本化（B2 的 debt_id/reason/policy 字段）由 journal_tx.kind+policy_version+memo
   承载，`debts` 表退化为投影。
9. **人工调账**：必须给出对手科目，禁止单腿（admin API 强制参数化），business_key 挂
   config_audit id——Q5 铁律落地。

### 2.4 不变量（写入时机械强制 + 周期审计）

- **J1**：每 journal_tx 的 Σamount = 0（写入事务内断言，不平即 rollback+P0——Q5 §4.2
  「1 个最小单位都算 P0」）。
- **J2**：business_key 唯一（DB 约束）→ 同一块/批次绝不二次入账（不变量#2 的 DB 级化）。
- **J3**：投影重放相等（影子对拍核心，见 §4；opening 起账后即为全量口径，见 §5）：
  `miner:payable` 科目余额 == balances.amount（逐地址）；
  `debt:receivable` == debts.remaining（逐地址）；
  `pool:fee_accrued` == Σ blocks.feeamount WHERE confirmed；
  `payout:settled` == 现行 paid 推导值；
  `block:revenue` == Σ blocks.reward WHERE confirmed。
- **J4**（阶段0 就先上）：Σ balance_changes(addr) == balances.amount（逐地址）——
  证明「余额可从事件日志重建」，即 docs/10 C1 过渡目标的持续在线证明。

## 3. 三阶段实施

### 阶段 0（极小改动，可并入任意批次先行）：过渡目标验证

- Reconcile 增加 J4 子检查（PG 全 SQL：`GROUP BY address` 比对，破则冻结+P0）。
  数据量护栏：balance_changes 永久保留，全表 SUM 随年增长——先按 (poolid,address) 聚合
  （已有索引），量级失控前引入月度 checkpoint 快照（Q5 §4.3 的二分定位思路），本阶段
  不需要。
- MemLedger 补对称：内存版流水 slice（同一 usage/tags 语义）+ 同一 J4 检查进 conformance。
- 交付判据：双实现 conformance 加「流水重放==余额」子测；dragonx/btc09 生产库上 J4 一次性
  核对通过。**★2026-07-17 已实测（Claude 只读 SQL，103.80 两生产库）：J4 双向全零**——
  dragonx 7 地址 / btc09 45 地址逐地址 Σbalance_changes==balances.amount 零失配，且无
  「有流水无余额行」的孤儿流。即 docs/10 C1 过渡目标「余额可从事件日志重建」**今天就
  在生产成立**，阶段0 只是把它固化成在线不变量（一旦哪天有人手工 SQL 改余额没配流水，
  立刻冻结+P0）。

### 阶段 1（本立项主体）：journal 影子双写

- 上述两表 + 各业务方法在**同一事务**内追加配平 journal（addBalanceTx 继续原样写
  balance_changes——旧流水一行不动，新旧并行）。
- 实现形态：每个业务方法组装一个 `journalBuilder`（收集腿→断言 Σ=0→同事务落库）。
  **balance_changes 与投影表的写入代码零改动**，journal 是纯追加面——review 面清晰，
  回滚 = 不写 journal 而已。
- MemLedger 同步实现内存 journal（保双实现 conformance 对称——这是本仓库两实现互相
  钉死语义的机制，不能única PG）。
- 影子校验：Reconcile 尾部跑 J3 全套（PG SQL 聚合），任何不等 → 只告警**不冻结**
  （影子期 journal 无权威；冻结仍由现行守恒式负责）。
- 起账（见 §5）+ conformance 全套扩展（每个现有子测后追加 journal 配平与投影相等断言，
  孤块/直付/退款/带费孤块每条路径都要有 journal 断言）。

### 阶段 2：权威翻转（单独小批次，影子期达标后才做）

- 翻转判据（都要满足）：①影子期 ≥ 2 周且横跨 ≥ 2 个真实打款周期；②期间发生过（或在
  预发环境注入过）孤块回滚、退款、直付各至少一次且 J3 全程 delta=0；③5850U PG16 全量
  conformance 绿。
- 翻转内容：J3 不等时的动作从「告警」升级为「冻结打款 + journal 为准人工修投影」。
  **投影表照旧存在照旧被读**——API/打款引擎读路径零改动，变的只是「谁说了算」。
- balance_changes 从此声明为 journal 的 `miner:payable` 腿投影（长期可做成 VIEW，不急）。

## 4. 影子对拍方案（「新旧账逐块 delta=0」的具体化）

- 粒度：每轮 RunOnce 的 Reconcile 尾部 = 每 ~10min 一次全量 J3；每笔写入 = J1 即时。
- 对拍失败处置（影子期）：`journal_shadow_mismatch` 告警事件（Hub 去重）+ 结构化日志带
  首个不等的 (account,address,journal值,投影值)——直接定位到笔，不用二分。
- 生产灰度顺序：dragonx（PG、有真打款、块频高）→ btc09（PG、直付无关但有费归集）→
  mem 币不灰度（内存 journal 只保 conformance 语义，重启即清，与 mem 账本同命——
  mem 币的审计级保障 = 迁 PG，不在本立项范围）。

## 5. 起账与迁移（不回填铁律）

- 部署首启（每币一次）：写 `opening:<ISO日期>` journal_tx——J3 追踪的每个科目都以
  **当时投影现值**起账（miner:payable=balances 逐地址、debt:receivable=debts 逐地址、
  pool:fee_accrued=Σfeeamount(confirmed)、block:revenue=Σreward(confirmed)、
  payout:settled=现行 paid 推导值），全部以 `opening:equity` 为对手腿轧平。
  policy_version='opening-snapshot'。自此每条 J3 恒等式对全量口径直接成立（无需
  增量换算）。
- 自此 J3 恒等式对「opening + 增量」成立；历史（opening 前）继续由 balance_changes/
  blocks/reconciliations 审计，**不伪造成 journal**。
- 回滚：阶段1 全程可直接停写 journal（表留着），无任何投影依赖它。

## 6. 与批次1/2、B2/B3 的关系

- **B2（追回/平账）**：结构化债务/错误追回不再单独设计表——journal 科目
  （debt:receivable / incident:loss / recipient:receivable）+ policy_version 即 B2 的载体。
  用户顺序里 ③B2 依赖本设计定稿，建议 B2 完整版随阶段1 一起实现（省一次账本手术）。
- **B3（版本化）**：journal_tx.policy_version 让每笔结算天然带版本戳；shares/blocks 的
  policy 列（docs/10 B3 TODO）等 policy registry 立起来后补，不阻塞本立项。
- **批次2 遗留两发现**（2026-07-17 真钱包验证发现，独立小修，可与阶段0 同批）：
  ①mem 币冷启动 chain-audit 误冻结风险 → 建议 mem 币默认禁用 chain-audit（配置
  `chainAudit:"off"` 显式打开才启）或持久化审计游标到 dataDir；
  ②PIVX 系 listsinceblock 无 blockheight → 游标不前进，每轮重扫回看窗（无害但费 RPC）
  → 适配器侧用「上次最大 confirmations 反推高度」或接受现状并文档化。

## 8. 待用户拍板的决策点

1. **渐进式三阶段 vs 一步到位**：本设计强烈推荐渐进（理由 §0/§1.1）；如果你想一步到位
   重写 Ledger 核心，需另立高风险方案（不推荐，违背「生产账本不可轻动」）。
2. **B2 是否并入 3c**（推荐并入，省一次账本手术；代价=批次3 范围变大）。
3. **mem 币策略**：内存 journal 只保语义对称、不承诺审计级（推荐）；或干脆推动 noctari
   类 mem 币迁 PG（另立运维事项）。
4. **批次2 遗留两发现**修法选择（§6：mem 币禁 chain-audit vs 持久化游标）。
5. 影子期时长（默认 2 周）与灰度顺序（默认 dragonx→btc09）。
