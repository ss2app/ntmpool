## 1. 事故：矿工「不定时连不上」的真因

### 1.1 现象
矿工大量反馈 `hk.ntmminer.com`（103.149.200.209）不定时中断、连不上，
或「一台矿机能连、另一台连不上」。

### 1.2 真因（2026-07-15 实查铁证）

```json
// /data/ntmpool-btc09/data/bans.json —— 抓现场时的实际内容
[{"target":"103.149.200.209","expiresAt":"2026-07-15T14:18:51Z",
  "reason":"auto: bad shares","strikes":4,"addedAt":"2026-07-15T12:44:13Z"}]
// /data/velkar/pool/pool-data/bans.json —— 同一模式，strikes 更高
[{"target":"103.149.200.209","expiresAt":"2026-07-15T08:13:40Z",
  "reason":"auto: bad shares","strikes":5,"addedAt":"2026-07-15T05:23:04Z"}]
```

**矿池在封自己的中转机。** 链条：

1. 209 用 `iptables DNAT + MASQUERADE` 转发 → 矿池看到的源 IP **全部**是
   `103.149.200.209`，矿工真实 IP 被抹掉（`internal/stratum/util.go: remoteHost()`
   取的是 `conn.RemoteAddr()`）。
2. `internal/stratum/autoban.go` 按 IP 统计恶意 share（badpow/malformed/dup
   占比 ≥50% 且样本 ≥10 条即封）。
3. 任一爬虫探针 / 坏矿机的垃圾包 → autoban 判定「这个 IP 是坏人」→ **封 209**。
4. 209 被封 = 走它的**全体矿工同时被拒**（`Accept` 后 BanChecker 直接断开）。
5. TTL 到期自动解封 → 大家又能连 → 表现为「**不定时**」中断。

**指数退避让事态恶化**：`TTL = 10min × 2^strikes`，封顶 24h；`strikes` 记在
banlist entry 里只涨不消。实测已到 4~5（封 1.5~3 小时），再涨几次就是一封一整天。

**「一台通、一台不通」** = 每个币的池各自独立 banlist（btc09 被封时 dragonx 没被封），
同一矿工的两台矿机自然一台通一台不通。

### 1.3 已排除（实测，勿再怀疑）

| 怀疑 | 实测结论 |
|---|---|
| 209 转发能力不足 | conntrack **258/32768**、负载 0.01、内存充足、网卡零错误、26 天未重启 |
| 209→103.80 链路差 | ping 100 包 **0% 丢包**，RTT avg 5.7ms |
| DNAT 并发瓶颈 | 同源 12 条并发 **12/12 全通**，握手 **2-3ms**，保持 45s 无踢除 |
| conntrack 表满 | 无 `table full` 丢包记录，用量 0.8% |
| 爬虫流量打满机器 | 负载/带宽均地板值；真凶不是流量，是**垃圾包触发误封** |
| 池日志有断连线索 | 各池近 24h 断连日志 **0 条** —— 因为压根没埋点（见 §5） |

**结论：转发层没坏，换 frp/gost 治不了病**（详见 §4）。

## 2. 止血（2026-07-15 已实施）

1. `POST /admin/v1/bans/delete` 解封 209（不重启、不断线），btc09 立即恢复；
   端到端验证：`209:8344` stratum 正常应答。
2. `/root/ntm-unban-guard.sh` + `ntm-unban-guard.timer`（每 30s）：
   发现中转机 IP（209 / 122.10.119.40）被 autoban 即自动摘除，并留档 strikes/TTL
   到 `/var/log/ntm-unban-guard.log`（该日志可用于量化误封频率）。
   - 自检方式：admin API 人为 ban `192.0.2.1`（RFC5737 保留址，零生产影响）→
     守护摘除 → 列表清空。已验证通过。
3. **副作用（可接受）**：期间 autoban 对中转机 IP 实质失效。这不是损失——
   在共用 IP 的现状下 autoban 永远打不中真正的坏人，只会误伤全体，**防护价值为零**。

> ⚠ 守护是**治标**。根治上线后应删除 timer + 脚本。

## 3. 根治：转发时保留真实 IP（PROXY protocol）

### 3.1 为什么这一个改动同时解决三件事

拿到真实 IP 后：
- **误封消失** —— autoban 封的是真正发坏 share 的那个矿工，不再是全体共用的门。
- **网页显示每个矿工 IP** —— 用户诉求。
- **探针/爬虫在中转机就挡掉** —— HAProxy stick-table 限速/拉黑，根本不碰池子。

### 3.2 好消息：池端代码早已写好，只是没启用

| 组件 | 位置 | 状态 |
|---|---|---|
| PROXY protocol **v1** 解包 | `internal/stratum/proxyproto.go` | ✅ 已实现（off/optional/required） |
| 配置开关 `proxyProtocol` | `internal/config/config.go:31` | ✅ 有（注释：「藏转发器后必须 required」） |
| 每真实 IP 连接数上限 `maxConnsPerIp` | `internal/config/config.go:34` | ✅ 有，生产未设（拿到真实 IP 后才有意义） |
| 端口总连接上限 `maxConns` | `internal/config/config.go:33` | ✅ 有 |

> **★ 关键约束：解析器只支持 v1**（`proxyproto.go` 只认 `PROXY TCP4/TCP6 ...` 文本行）。
> HAProxy 必须用 `send-proxy`（v1），**不是** `send-proxy-v2`，否则池端解不开、全员断线。

### 3.3 转发器落在哪台机器

**建议：新机 103.231.14.85（Ubuntu 22.04）做新中转机，不动 209。**

理由：
- **209 是 Debian 9 stretch，2017 年发行、早已 EOL**。实测 `apt-get update` 报
  `Release file` 全部失效（源已下线），装 HAProxy 要折腾 archive.debian.org 或
  手搓二进制，且这台机器再无安全更新。
- 新机全新 Ubuntu 22.04，2 核 1G 29G，`apt install haproxy` 即可（HAProxy 2.4，
  跑几千条 stratum 长连接毫无压力）。
- **零风险灰度**：新机独立验证，完全不碰 209 现有生产流量；验证通过再切流。
- 顺带消除单点：209 保留作备用线路，两条线路并存。

> 备注：两台机器都在**高防 SYN 代理**后面（实测特征：服务器上根本没监听的端口
> 61234/12345 也照样 TCP 握手成功）。这与本次事故无关，但意味着中转机看到的连接
> 可能已被上游代理过一手，PROXY protocol 头由**我们的 HAProxy** 生成，不受影响。

### 3.4 HAProxy 配置骨架（待审）

```haproxy
global
    maxconn 20000
    log /dev/log local0

defaults
    mode tcp
    timeout connect 10s
    timeout client  1h        # stratum 长连接，别用默认 50s
    timeout server  1h
    option tcplog             # ★ 每条连接的真实 IP 落日志（当前完全缺失）

# 探针/爬虫在中转机就挡掉：单 IP 连接数 + 新建速率限制
backend be_btc09_pplns
    server pool 103.80.18.140:18344 send-proxy      # ★ v1，不是 send-proxy-v2
frontend ft_btc09_pplns
    bind :8344
    stick-table type ip size 200k expire 10m store conn_cur,conn_rate(60s)
    tcp-request connection track-sc0 src
    tcp-request connection reject if { sc0_conn_cur gt 32 }      # 单IP并发上限
    tcp-request connection reject if { sc0_conn_rate gt 60 }     # 单IP新建速率
    default_backend be_btc09_pplns
# 其余端口同构：5333/5444/15333/13333/18345/4455/4456/4457
```

> 阈值（32 并发 / 60 次每分钟）是**初值待定**，必须先用 `option tcplog` 观察真实
> 矿工分布再定 —— 矿场客户可能单 IP 几十台矿机，**拍脑袋设小 = 又一次误伤全员**。
> 铁律：先观察，后收紧。

### 3.5 灰度切换时序（★ 顺序错 = 全员断线）

```
① 池端先开 optional（有 PROXY 头就解，没头当直连）
   → 此时 209 的 DNAT 直连流量仍正常，新机的 PROXY 流量也能认
   → 改 config.json + 重启池（会断一次线，选低峰期）
② 103.80 防火墙白名单加新机 IP（见 §5 隐患，脚本要同步改）
③ 新机 HAProxy 起，先只接一个币的一个端口，用我们自己的矿机验证：
   → 池日志/网页应显示**矿机真实 IP**，而不是中转机 IP
④ 验证通过 → 逐币把 HAProxy 端口补齐 → 观察 1~2 天
⑤ 切流：DNS hk.ntmminer.com 指新机（或先给矿工新地址并行跑）
⑥ 全部矿工迁移完 → 池端收紧 required（防伪造直连）→ 删 unban-guard
⑦ 收紧后才可启用 maxConnsPerIp（阈值按 ③④ 观察到的真实分布定）
```

**绝不能**先开 `required`：DNAT 直连没有 PROXY 头，会被池端直接拒 → 全员断线。

### 3.6 回滚

| 步骤 | 回滚动作 |
|---|---|
| ① optional | 改回 `off` + 重启池（optional 本身兼容直连，风险极低） |
| ③④ HAProxy | 停 HAProxy；矿工继续走 209 DNAT，无感 |
| ⑤ DNS 切流 | DNS 切回 209；TTL 期内两条线路并存，不断线 |
| ⑥ required | 改回 `optional` + 重启池 |

## 4. 为什么不用 frp / gost

| 方案 | 判断 |
|---|---|
| **frp** | ❌ 内网穿透工具，场景是「矿池无公网 IP」——我们有。要在池端跑 frpc 反连隧道，**隧道一断全员掉线**，凭空增加单点。 |
| **gost** | ❌ 能做，但没必要。它的强项是隧道/加密（我们不需要），作为纯 TCP 前置是用户态转发，比内核态 DNAT 慢、更吃 CPU。 |
| **保持 DNAT** | ✅ 内核转发，实测握手 2-3ms、12/12 并发、0% 丢包——**性能上它就是最优解**。 |
| **HAProxy + PROXY v1** | ✅ **推荐**。20 年工业验证的 TCP 负载均衡；唯一能同时给出真实 IP + stick-table 限流 + 健康检查 + 连接日志。 |

**核心认知**：问题从来不是「用哪个转发软件」，而是「**转发时有没有保留真实 IP**」。
任何抹掉 IP 的方案（含 frp/gost 的默认配置）都会复现同一个误封事故。

## 5. 连带发现的隐患

### 5.1 ⚠ 防火墙脚本有两份，只有一份是真的（排查陷阱）

**曾据此误报「定时炸弹」，已纠正——教训值得留档：**

```
/root/ntm-firewall.sh            inode 1176  Jul 12   ← 过期副本，不是它在跑
/usr/local/sbin/ntm-firewall.sh  inode 4633  Jul 14   ← ★ service 真正执行的
```

两者是**独立文件**（非硬链接），内容曾不一致：旧副本的 `STRATUM_209` 缺
`4455,4456,4457,5511,5512`，而真正执行的那份早已包含。当时只看 `/root/` 那份，
就误判「重启会打掉 noctari 端口」——**其实规则与生效脚本完全一致，没有炸弹**。

> **教训：认 `systemctl cat <svc> | grep ExecStart`，只读它指向的那个路径。**
> `/root/` 下的同名脚本是历史副本，是排查陷阱。

已处理：2026-07-15 把 `/usr/local/sbin/` 的现行版同步覆盖到 `/root/`，两份现已一致，
消除下次再读错的可能。改防火墙一律改 `/usr/local/sbin/ntm-firewall.sh`。

### 5.2 可观测性缺失（本次排查最大的阻力）

- **autoban 静默**：`autoban.go:52` `_ = a.banner.Ban(...)` 不打日志 → 封了没人知道。
- **BanChecker 拒连静默**：Accept 后直接断，无日志 → 矿工连不上，池日志一片干净。
- **无连接生命周期埋点**：各池近 24h `disconnect|reset|EOF` 命中 **0 条**。

→ 结果：矿工断线数周，日志零线索，只能靠翻磁盘上的 `bans.json` 抓现行。

**建议（与 §3 一起做）**：
- `Ban()` 触发时 `log.Printf` 打 target/reason/strikes/TTL（**必须**，代价极小）。
- BanChecker 拒连时打一行（可采样，防日志洪水）。
- 连接 accept/close 打点（含真实 IP，PROXY protocol 上线后才有意义）。

## 7. 实施记录与剩余项（2026-07-15）

### 7.1 落地清单

- **新机 103.231.14.85**：SSH 改 8422+密钥（密码已关）；HAProxy 2.4.30。
  配置 `/etc/haproxy/haproxy.cfg`（含完整注释与端口映射表）。
  - ★ `timeout client/server 1h`：HAProxy 默认仅 **50s**，stratum 长连接会被反复踢下线。

    这是目前**唯一的连接级可观测性**（含矿工真实 IP），补了 §5.2 的缺口。
- **池端**：全部 PROXY 端口用 `POST /admin/v1/coins/{id}/ports` **热加**，零重启。
  - ⚠ URL 必须带 `/ports`；POST 到 `/admin/v1/coins/{id}` 会返回 `Method Not Allowed`。
