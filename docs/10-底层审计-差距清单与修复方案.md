## 0. 总判断

NTMPool 的**核心正确性护栏大部分已达标**，且很多是行业里开源池普遍没做对的点：
拆步打款、sendmany 超时不自动重发、孤块按 hash 逐字节比对、算力窗口与 PPLNS 解耦、
vardiff pendingDifficulty、Notifier 推+拉双通道、JobKey 语义去重、守恒对账冻结打款、
同源共识库金锚自检。**不是推倒重来，是补几个明确的洞。**

差距集中在三块，按用户当前最关心排序：
1. **攻击/拉黑 IP 的代码级护栏**（我们真实踩过 MASQUERADE 连坐事故，但代码里仍无硬闸）——**最高优先，本次先做**。
2. **打款审计闭环**（链上反查对账 chain-to-book——抓"未知出账"和"上链了没记账"）。
3. **账本升级为不可变复式 journal**（最大、最伤筋动骨，单独立项，不塞进快改）。

## 2. 差距清单（分级）

### 【A 档 · 攻击/拉黑 IP 护栏——本次先做，直接命中用户诉求 + 真实事故】

**A1. autoban 无受信转发机/白名单硬护栏（=我们连坐事故的代码根因）**
- 现状：`stratum/autoban.go:52` 直接 `a.banner.Ban(a.ip, ...)`；`banlist.List` 只有
  Ban/Unban/Banned/Strikes/Entries，**无任何 whitelist/受保护 CIDR**。目前只靠服务器上
  `ntm-unban-guard.sh` 脚本每 30s 摘除中转机 IP 兜底（治标）。
- 问答依据：Q4 §2.6 / Q8-A。**铁律：经 NAT/代理失真的 IP 不得作为高爆炸半径处罚的唯一主体。**
- 要做：
  1. `banlist` 增受保护名单（protected CIDR 列表，配置注入）：中转机/节点/admin/VPN 网段。
     `Ban()` 命中受保护名单→**拒绝写入 + 打 P0 日志 + 返回哨兵错误**，autoban 永远 ban 不到它们。
  2. autoban **爆炸半径护栏**：单条 ban 决策若会命中受保护名单或影响面异常→降级为告警/限速，不执行。
  3. **"坍缩到单 IP"检测**：某端口 ≥N%（默认 90%）在连显示同一个源 IP → 判 PROXY 链路失效
     （而非真有人攻击）→ 自动**临时禁用该口 IP-autoban** + 告警。这是"再来一次 MASQUERADE"的自动免疫。

**A2. autoban / 拒连 静默无日志（docs/09 §5.2 早标记，代码至今没补）**
- 现状：`autoban.go:52` `_ = a.banner.Ban(...)` 吞返回值、无日志；BanChecker 拒连也无日志。
- 后果：矿工断线数周、池日志零线索，只能翻磁盘 bans.json 抓现行（就是上次排查地狱）。
- 要做：`Ban()` 触发打结构化日志（target/reason/strikes/ttl/coin）；BanChecker 拒连打一行（可采样防洪水）；
  连接 accept/close 打点（含 verified 真实 IP）。**代价极小，收益巨大。**

**A3. verified_client_ip 与 transport_peer_ip 未显式分型**
- 现状：`remoteHost(conn)` 取 `conn.RemoteAddr()`（PROXY 解包后是真实 IP，没解就是 socket 对端），
  但类型上二者混同，ban 决策拿到什么用什么。
- 问答依据：Q4 §3.1（ban 输入类型只能是 verified IP；PROXY 解析失败绝不退化成"把代理 IP 当矿工 IP"）。
- 要做：连接对象上显式区分 `TransportPeerIP`（socket 对端）/`VerifiedClientIP`（仅受信 edge 发 PROXY 头才生成）/
  `IPProvenance`（DIRECT/PROXY_V1/PROXY_V2）；autoban 只吃 VerifiedClientIP，拿不到 verified 时**只按连接/会话断，不按 IP ban**。

**A4. 分级校验 + 有界资源（防垃圾数据 DoS）自查**
- 问答依据：Q4 §2.1 阈值表 / Q8-U。要做（核对现状，缺则补）：未 authorize 就狂发→秒断计数；
  单条消息字节上限（16-64KiB）；JSON 嵌套深度上限；未授权消息数/字节上限；握手超时；
  PoW 验证队列有界（RandomX 类昂贵算法独立并发池，先廉价检查后进队列）。

### 【B 档 · 打款审计闭环——命中"审计/追回/平账/未上链却记账"】

**B1. 无 chain-to-book 反向对账（抓"未知出账"和"上链了没记账"）**
- 现状：只有内部守恒 `Reconcile`（Σ已确认=Σ已付+余额+费+在途+债务，账自洽）。
  **没有**扫钱包实际出账逐笔反查"这笔是不是我授权的 intent"的扫描器。
- 问答依据：Q2 §4.2 / Q8-C 兜底 / Q9 审计#1。**内部账自洽只证明"数据库同意自己"，不证明币真的在。**
- 要做：新增 `ChainToBookReconciler`（每币周期跑）：
  - 列钱包近期 outbound tx（listtransactions/z_listreceived 等，按适配器能力）；
  - 每笔按 txid/outputs 反查是否对应已授权 batch/intent；
  - 命中未知出账（有转出但无 intent）→ **立即冻结该币打款 + P0 告警**（私钥泄漏/绕过/bug 的唯一早期信号）；
  - 反向：链上有池 coinbase 收入但 blocks 表无记录 → 告警 + 可一键补建 round（docs/05 场景 B 已设计，补实现）。

**B2. 打款追回/平账机制不完整（多打/打错地址/孤块已付）**
- 现状：孤块有 debts 追缴（占比追缴、未来收益抵扣）。但"多打了一倍/打给错误地址"这类
  **非孤块的错误追回**没有标准流程与账户。
- 问答依据：Q2 §5 / Q5 §5。要做：
  - 债务记录结构化（debt_id/source/reason=reorg|duplicate|overpay|fraud/principal/recovered/remaining/policy_version），
    **不用 balance=-123 表示**（现状可能就是负余额，需核对）；
  - 追缴顺序与比例版本化（PPS orphan=0%池担；PPLNS 早付=最终100%每期抵25-50%；fraud=100%）；
  - 错误收款进 `incident_loss`/`recipient_receivable`，绝不悄悄把矿工余额改负。

**B3. 版本化不全（历史事件不能被当前配置重新解释）**
- 现状：有 config_audit + config.state.json。但 share/block/reward/payout 是否都 stamp
  了 settlement_policy_version / fee_policy_version / rounding_policy_version 需核对补齐。
- 问答依据：Q1 §6.13 / Q9 inv#5。要做：结算相关表补 policy_version 列 + 结算时固化，
  改费率/改确认数/改结算规则一律新 version，**绝不追溯重算旧块**。

### 【C 档 · 大改，单独立项，本次不做（仅记录）】

**C1. 账本升级为不可变复式 journal**
- 现状：余额投影模型（memledger/pgledger）+ 守恒 Reconcile + balance_changes 审计流水。
- 问答依据：Q1 §4.6 / Q5 §4 / Q8-P。codex 力荐 append-only double-entry（借贷分录、余额只是可重建投影、
  修正只用补偿分录）。**这是最伤筋动骨的改动，且我们已有守恒对账覆盖了大半安全性**——
  单独立项、单独设计评审，绝不塞进本次快改（生产已验证的账本不可轻动）。
- 过渡目标（可先做）：确保余额能**完全从 append-only 事件日志重建**（balance_changes 若已满足即达标）。

**C2. PROXY protocol v1 → v2**（G4）
- 现状：`proxyproto.go` 仅解 v1 文本头。codex 建议 v2（IPv6/TLV/健壮）。
- 优先级低：v1 生产可用（docs/09 已上线）。作为 A 档改动的顺带项：解析器同时认 v1+v2（嗅探首字节），
  HAProxy 侧可继续 send-proxy(v1) 不动。**低风险增量，可并入 A 档批次。**

**C3. effort 多层漏斗监控**（Q5 §7）
- 建立 accepted work → local candidate → node accepted → canonical → mature 五层指标，
  用于早期发现共识 bug（effort 长期偏离 100%）。属可观测性增强，非正确性护栏，排 C 档。

## 4. 一页纸：10 条不可违反的核心不变量（刻进核心，验收总纲，摘自 Q9）

1. 未过完整验证并可靠持久化，绝不回 `Share Accepted`。
2. 同一 share/block/settlement/payout 事件全系统最多产生一次经济效果。
3. work 只从服务端预分配整数 target 推导；金额只用最小单位整数；核心账务禁浮点。
4. 每笔余额变化对应借贷相等的不可变分录；余额只是可重建投影。
5. 结算绑定不可变 policy version；PPLNS 只按累计 work；分配总额与可分资产严格守恒。
6. 矿工可提现负债必须由成熟 canonical 资产/明确补贴/足额隔离准备金支持。
7. 块状态只由 canonical hash + chainwork + 成熟规则决定；orphan/reorg 只用补偿分录，禁删历史。
8. 出币必先有唯一持久化 payout intent；RPC 返回未知时查清链上真相前禁止重付。
9. 链上受控资产与资产账出现任何无法解释差异→受影响币立即停结算停打款。
10. 外部输入不可信且资源消耗有界：PROXY 只信受信 edge、受信转发机永不 autoban、连接与验证队列永不无界。
